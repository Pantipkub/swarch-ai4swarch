**สรุปการประชุม**
1. **สถาปนิก:** อธิบายว่า RabbitMQ แยกงานหลังสั่งซื้อออกจาก checkout ทำให้ email, loyalty และ analytics ทำงานแยกกันได้ และเพิ่ม consumer ใหม่ได้โดยไม่ผูกกับ order service จากนั้นยอมรับว่า ADR ยังต้องระบุให้ชัดว่าจะเกิดอะไรขึ้นถ้าตัดเงินสำเร็จแต่ event ยังไม่ถูกบันทึกอย่างทนทาน และขอให้คณะกรรมการพิจารณาว่าเป้าเวลาของ loyalty ยังทำได้หรือไม่เมื่อ broker ล่ม
2. **AI analyst:** นำเสนอผลรีวิวของ AI โดยไม่ใส่ความเห็นของตัวเอง
   - ช่วงระหว่างตัดเงินกับเขียน outbox อาจทำให้ตัดเงินสำเร็จโดยไม่มี event ที่ทนทาน
   - ต้องระบุพฤติกรรมของ relay, การรับประกันการกู้คืน และการจัดการเมื่อ loyalty ล่าช้าให้ชัดกว่านี้
   - ช่วง peak ความต้องการส่งอีเมลเกิน throughput ของ MailFast ทำให้ backlog โตขึ้นเรื่อย ๆ
   - ข้ออ้างที่เปรียบเทียบ RabbitMQ กับ Kafka บางข้อไม่มีหลักฐานรองรับเพียงพอ
   - ตัวอย่าง peak 30 นาทีเป็นสมมติฐานประกอบการอธิบาย ไม่ใช่ requirement ที่ scenario กำหนด
3. **PO:** ถามว่าลูกค้าและธุรกิจรับอีเมลยืนยันที่ล่าช้าได้หรือไม่ เมื่อยอดสั่งซื้อเกินขีดจำกัดของ MailFast ที่ 200 orders/s แต่ส่งอีเมลได้สูงสุด 50/s ถ้าอัตรานี้คงอยู่ backlog จะโตราว 9,000 ฉบับต่อนาที และถามว่าเป้า loyalty 1 นาทีจะรับมืออย่างไรเมื่อ broker ล่ม คณะกรรมการต้องได้การตัดสินใจทางธุรกิจที่ชัดเจนเรื่องความล่าช้าที่ยอมรับได้และความคาดหวังในการกู้คืน แทนที่จะสมมติว่าการประมวลผลแบบ async ทำได้ตามเป้าโดยอัตโนมัติ
4. **SRE:** ถามว่า outbox relay จะรันอย่างไร จะ retry ความล้มเหลวอย่างไร และจะจัดการข้อความซ้ำอย่างไร แนะนำให้เขียน monitoring, alerting, เกณฑ์ความลึกของคิว, การจัดการ dead-letter และขั้นตอนการกู้คืนไว้ในเอกสาร และย้ำว่าทีมต้องพิสูจน์ throughput และ availability ภายใต้สภาวะจริง ADR ไม่ควรสมมติว่า broker และ relay ที่เสนอรับ peak workload และเป้าเวลาของ loyalty ได้เอง
5. **Security:** ชี้ว่า event ในคิวอาจมีอีเมลลูกค้าและข้อมูลที่เกี่ยวกับ order ADR ระบุเรื่องข้อมูลส่วนบุคคลในคิวไว้เป็น open question แต่ยังไม่กำหนดมาตรการด้าน privacy และ security จึงขอให้ทีมระบุว่า
   - event ต้องมี field อะไรบ้าง
   - ใครมีสิทธิ์ publish และ consume
   - การเชื่อมต่อกับ broker ยืนยันตัวตนและป้องกันอย่างไร
   - ข้อความและ dead-letter เก็บไว้นานเท่าไร

   ข้อมูลอ่อนไหวไม่ควรค้างในคิวนานเกินจำเป็น และต้องจำกัดสิทธิ์เข้าถึงข้อความและ log การปฏิบัติงาน
6. **สถาปนิก:** เห็นด้วยว่า ADR ต้องระบุ failure semantics ให้ชัด มีเกณฑ์ยอมรับทางธุรกิจที่ชัดเจน และมีข้อกำหนดด้าน security ที่เข้มขึ้น จึงเสนอให้ปรับ ADR ก่อนเริ่มพัฒนา แทนที่จะถือว่าการออกแบบปัจจุบันผ่านการพิสูจน์แล้ว

## 3. บันทึกผลการตัดสินใจ (8 นาที, ทำร่วมกัน)

**ADR ที่รีวิว:** ADR-0002 "Publish an `OrderPlaced` event to RabbitMQ for post-order actions" โดย Pitchanan Thaiphayak (`docs/adr/0002-*.md` และ `exercise/outputs/3-review.md` ใน repository ของ Pitchanan) การตัดสินใจที่รีวิวคือใช้ RabbitMQ แบบ self-hosted ร่วมกับ outbox และ consumer ที่แยกอิสระสำหรับงานหลังสั่งซื้อ
**สมาชิกและบทบาท:** Pitchanan Thaiphayak (สถาปนิก), Kotchapan Lertpanyaroj (AI analyst), Pon Kittinaraporn (Product owner), Piyapanchanok Meeboonsalang (SRE), Chayutpong Soisri (Security)

**มติ:** อนุมัติโดยมีเงื่อนไข

**สิ่งที่ต้องแก้ไข:**
1. **ระบุความสอดคล้องระหว่างการตัดเงินกับ outbox ให้ชัด:** เขียนขอบเขตของ transaction ระหว่างการตัดเงิน, การบันทึก order และการ publish event และกำหนดพฤติกรรมการกู้คืนและการ reconcile เมื่อเกิดความล้มเหลวระหว่างขั้นตอนเหล่านี้
2. **ระบุการรับประกันการส่งและการกู้คืน:** เขียนการทำงานของ relay, retry, การจัดการข้อความซ้ำ, การจัดการ dead-letter, monitoring และการกู้คืน และพิสูจน์ว่าระบบรับ workload และเป้า latency ได้
3. **กำหนดความคาดหวังระดับธุรกิจ:** ตกลงกับฝ่ายธุรกิจเรื่องความล่าช้าของอีเมลที่ยอมรับได้, เวลาเคลียร์ backlog และเป้า loyalty 1 นาทีเมื่อ broker ล่ม ส่วนการเปรียบเทียบ broker ต้องมีหลักฐานรองรับ ไม่ใช่ข้ออ้างลอย ๆ
4. **เพิ่มข้อกำหนดด้าน security และ privacy:** ใส่ข้อมูลส่วนบุคคลใน event ให้น้อยที่สุด และกำหนดการยืนยันตัวตน, การให้สิทธิ์, การป้องกันการเชื่อมต่อกับ broker, ระยะเวลาเก็บข้อมูล และสิทธิ์เข้าถึง dead-letter queue
5. **พิสูจน์การออกแบบก่อนขึ้น production:** ทดสอบ peak throughput, broker ล่ม, consumer ล้มเหลว, การส่งข้อความซ้ำ และพฤติกรรมการกู้คืน

**ใครยกประเด็นใด** ระบุทุกข้อกังวลที่คณะกรรมการอภิปราย

| # | ข้อกังวล | ผู้ยกประเด็น (ผลรีวิว AI / สถาปนิก / PO / SRE / security) | อยู่ในผลรีวิวของ AI หรือไม่ | AI มีทางรู้ได้หรือไม่ เพราะเหตุใด |
|---|---|---|---|---|
| 1 | การตัดเงินอาจสำเร็จโดยไม่มี event ที่บันทึกไว้อย่างทนทาน | สถาปนิก และ SRE | ✅ | รู้ได้ AI อนุมานความเสี่ยงด้าน consistency ได้จากขอบเขต transaction ที่ ADR เขียนไว้ แต่นโยบายการกู้คืนที่ถูกต้องต้องให้มนุษย์ตกลงกัน |
| 2 | loyalty อาจไม่ทันเป้า 1 นาทีเมื่อ broker ล่ม | PO และ SRE | ✅ | รู้ได้บางส่วน AI ชี้ความขัดแย้งได้ แต่ลำดับความสำคัญทางธุรกิจและระดับการลดบริการที่ยอมรับได้ ต้องให้ผู้มีส่วนได้ส่วนเสียตัดสิน |
| 3 | backlog อีเมลอาจโตขึ้นในช่วง peak | PO | ✅ | รู้ได้บางส่วน AI คำนวณอัตราการโตของ backlog ได้ แต่ความล่าช้าที่ยอมรับได้และระยะเวลาของ peak ต้องยืนยันกับฝ่ายธุรกิจ |
| 4 | ข้ออ้างที่เปรียบเทียบ broker อาจไม่มีหลักฐานรองรับ | สถาปนิก | ✅ | รู้ได้ AI ชี้ข้อความที่ไม่มีหลักฐานและขอหลักฐานเพิ่มได้ |
| 5 | ข้อมูลส่วนบุคคลอาจรั่วหรือค้างอยู่ในคิวและ dead-letter | Security | ⚠️ ไม่ได้เป็นข้อค้นพบหลักในผลรีวิว แต่ ADR ระบุเรื่อง privacy ไว้ใน open questions | รู้ได้บางส่วน AI ชี้ open question และเสนอมาตรการได้ แต่องค์กรต้องกำหนดข้อกำหนดด้าน security และ privacy เอง |

**ข้อค้นพบที่ดีที่สุดของ AI** (ที่มนุษย์มองข้ามไป): ช่องว่างด้าน consistency ระหว่างการตัดเงินกับ outbox เพราะเปิดให้เห็น failure scenario ที่สถาปัตยกรรมต้องจัดการให้ชัด และช่วยให้คณะกรรมการแยกได้ว่า "มี outbox" ไม่ได้แปลว่า "รับประกันว่าการตัดเงินกับ event สอดคล้องกัน"
**ข้อค้นพบที่อ่อนที่สุดของ AI** (กว้างเกินไป ผิด หรือไม่เกี่ยวข้อง): ตัวอย่าง peak 30 นาทีอาจทำให้เข้าใจผิดว่าเป็น requirement ของ scenario การคำนวณ backlog มีประโยชน์ แต่ระยะเวลาของ peak เป็นสมมติฐาน และควรติดป้ายว่าเป็นสมมติฐาน
